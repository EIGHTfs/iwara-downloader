# 总表 JSONL 改造（iwara）

- 日期：2026-10-15
- 范围：**只改 `json/index/iwara-index.json` 总表的存储格式与读层**。
  **不改**逐条 `<id>.json` sidecar、**不改** `json/profile/`、**不改**搜索。
- 状态：已实现并部署端验收

## 一、为什么只改总表

部署端实测 `json/index/` 规模：**442 个文件 / 0.64MB**（`iwara-index.json` 0.32MB + 441 个 sidecar），
`json/profile/` 1406 个文件 / 0.45MB。

结论：**iwara 侧的性能收益很小**（总表本来只有 0.32MB，重写是毫秒级）。改总表的实际价值是：

1. 与 gbmd 侧**格式统一**（两仓索引都用同一套 `jsonl-store` 通用件）
2. 具备**追加**能力（总表单条更新不必再整份读+写）
3. 去掉 2 空格缩进，体积更小

逐条 sidecar 是**按单文件被单独服务**的（`/api/index-sidecar` 供 aria2 短链拉取），改格式没有收益、
反而增加对外契约风险 ⇒ **保持原样**。`json/profile/` 同属另一套索引，本次不动。

## 二、怎么改

### 格式

```
{"_":"meta","schema":2,"shape":"flat"}
{"t":"video","k":"06nRjMFKIRbZ1s","v":{"name":"…","username":"…","title":"…","fileId":"…"}}
```

- 一条记录 = 一个视频条目（`t` 恒为 `video`）
- 同键重复出现 ⇒ last-wins（与整文件重写语义一致）
- 旧总表若为包裹形态 `{schema:"iwara-index/1",videos:{…}}`，迁移时把它自己的 `schema` 存进
  `legacySchema`（避免与存储层版本号撞名），回拼时还原

### 代码落点（`server/lib/video-index.js`）

| 位置 | 改动 |
|---|---|
| 新增 `CATALOG_BASE` / `serverCatalogBase()` | 总表基路径（不带后缀），供存储层在 `.jsonl` / `.json` 间选择 |
| 新增 `readCatalogAt(root)` | 双读并返回**普通对象**（见下「踩过的坑」） |
| 新增 `migrateCatalogToJsonl()` | 每次进程只跑一次的一次性迁移（幂等；旧文件进 `.trash`） |
| `loadCatalogMap()` | 改走双读 + 读取前同步迁移 |
| `saveCatalogMap()` / `patchCatalog()` | 落盘改为 JSONL 原子写 |
| `readEntry()` | 总表兜底改走双读（原来直接读 `.json`） |
| `catalogFileBuffer()` | **未改**：仍产出 2 空格缩进的扁平 JSON |

**导出/导入也必须同一格式（2026-10-15 追加）**：改了存储却把导出留在缩进 JSON 是不自洽的，
所以导出一起改成 JSONL：

| 端点 | 改造后 |
|---|---|
| `GET /api/index/export` | 附件名 `iwara-index-<日期>.jsonl`、`Content-Type: application/x-ndjson`，内容**就是磁盘索引本身**（一行 meta + 一行一条） |
| `POST /api/index/import` | 吃导出的 JSONL 原文（`{json:"<文本>"}` 或直接 POST 原文），同时兼容旧 JSON（`{videos:…}` / `{items:[…]}` / `{dump:…}` / 扁平 map） |
| `GET /api/search/export` | `iwara-search-records-<日期>.jsonl`（一行 meta + 一行一条记录） |
| `POST /api/search/import` | 同上：JSONL 与旧 JSON（数组 / `{results:[…]}`）都吃 |
| 前端（`server/public/app.js`，项目自有） | 两个下载名改 `.jsonl`；导入改为**把文件原文直接发给服务端**（不在浏览器 `JSON.parse` —— JSONL 整体不是合法 JSON） |

证据：单测里有一条**往返断言** —— 导出 → `importPayload` 原样导入 → 再导出，**逐字节一致**。

`GET /api/index`（列表）与 `GET /api/index-sidecar`（单条 sidecar）**未改** —— 后者是你明确要求不动的「小的」。

### 为什么迁移必须「同步、且在读取之前」

若异步：迁移期间新落的总表会先建出**只含新记录**的 `.jsonl`；迁移脚本见目标已存在即跳过
⇒ 下次加载以 `.jsonl` 为准 ⇒ **旧总表丢失**。同步执行没有这个窗口。

## 三、踩过的坑（自查发现，已修）

**现象**：迁移成功（`.jsonl` 已生成、旧文件已进 `.trash`），但读总表得到的却是 `{}`，
`hasVideo()` 恒为 false。

**根因**：`readCatalogAt()` 初版直接返回 `Map`，而 `loadCatalogMap()` 用
`Object.assign(map, readCatalogAt(r))` 合并多个根 —— **Map 的条目不是自有可枚举属性**，
`Object.assign` 只会复制出一个空对象。

**解决**：`readCatalogAt()` 改为遍历 `Map` 转成普通对象后返回。

**防再犯**：凡「返回集合」的内部函数，先看清调用方是用 `Object.assign`/展开合并（⇒ 必须普通对象），
还是用 `Map` API 访问；本次由新增的等价性单测当场抓到。
