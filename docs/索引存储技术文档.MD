# 索引存储技术文档

- 适用范围：`json/index/` 下**总表**的存储格式、读层、写层、后端选择、迁移与排查
- **不适用**：逐条 `<id>.json` sidecar（刻意保持原格式）、`json/profile/`、查询/搜索业务逻辑、下载任务存储
- 当前状态：**JSONL 优先**，SQLite 仅在显式开关下启用

---

## 一、分层结构

```
业务层   server/lib/video-index.js（688 行）
         · 总表业务语义：loadCatalogMap / saveCatalogMap / patchCatalog / readEntry / hasVideo
         · sidecar 另成一路：writeFetchableSidecar / readFetchableSidecar（本体系不含）
              ↓ 只调用两个入口
存储层   server/lib/index-store.js（335 行）
         · 后端选择与回落（默认 JSONL；SQLite 需显式开关）
              ↓
         server/lib/jsonl-store.js（365 行）
         · JSONL 读写、原子替换、坏行容错、JSON↔JSONL 双读、迁移驱动
```

**唯一契约**：`readIndex(fileBase)` 恒返回

```js
{ format, file, meta, records, badLines, json, bytes }
```

`writeIndexAtomic(fileBase, meta, records)` 恒返回 `{ ok, file, bytes? }`。
上层只吃这一份结构 ⇒ 换后端时业务层零改动。

---

## 二、为什么只改总表，不改 sidecar

部署端实测 `json/index/` 规模：**442 个文件 / 0.64MB**（总表 `iwara-index.json` 0.32MB + 441 个 sidecar），
`json/profile/` 1406 个文件 / 0.45MB。

- **总表**（0.32MB）：改成 JSONL，价值是 ① 具备追加能力 ② 去掉缩进、体积更小 ③ 单行损坏不再毁掉整份总表
- **sidecar**（`<id>.json`，几百字节/个）：**按单文件被单独服务**（`/api/index-sidecar` 供 aria2 短链拉取），
  改格式**没有性能收益**，反而增加对外契约风险 ⇒ **保持原样**
- **`json/profile/`**：同属另一套索引，本次不动

⇒ 收益判断：总表本来只有 0.32MB，重写是毫秒级，**性能收益很小**；这次改造的真实价值是格式自洽与追加能力。

## 三、数据格式

### 3.1 文件布局

```
json/index/
├── iwara-index.jsonl       ← 当前格式（总表）
├── iwara-index.json        ← 旧格式，仍可读（双读）
├── <id>.json               ← sidecar，格式不变（缩进 JSON）
└── .trash/<时间戳>-<原名>   ← 迁移/清理的回收站
```

### 3.2 记录模型

```jsonl
{"_":"meta","schema":2,"shape":"flat"}
{"t":"video","k":"06nRjMFKIRbZ1s","v":{"name":"…","username":"…","title":"…","fileId":"…"}}
```

- 一条记录 = 一个视频条目，`t` 恒为 `video`
- **同键重复 ⇒ last-wins**，与「整文件重写」语义一致
- 旧总表若是包裹形态 `{schema:"iwara-index/1",videos:{…}}`，迁移时把它的 `schema` 存进
  **`legacySchema`**（避免与存储层版本号撞名），回拼时还原

## 四、读路径（一次加载的完整生命周期）

1. `loadCatalogMap()` → `readCatalogAt(root)`
2. **读取前同步执行一次性迁移**（`migrateCatalogToJsonl()`，幂等；原因见第六节）
3. `index-store.readIndex(CATALOG_BASE)`：显式开启 SQLite 才先读库；否则 **文件优先**（`.jsonl` → `.json`）
4. 记录 → 普通对象（**不是 Map**，原因见第五节）
5. `readEntry()` 的总表兜底同样走双读；`hasVideo()` / 列表端点读到的是同一份数据

**多根合并**：`catalogRoots(downloadRoot)` 可能给出多个根，`loadCatalogMap()` 用
`Object.assign(map, readCatalogAt(r))` 逐根合并。

---

## 五、踩过的坑：返回 Map 还是普通对象

**现象**：迁移成功（`.jsonl` 已生成、旧文件已进 `.trash`），但读总表得到的是 `{}`，`hasVideo()` 恒为 false。

**根因**：`readCatalogAt()` 初版直接返回 `Map`，而 `loadCatalogMap()` 用
`Object.assign(map, readCatalogAt(r))` 合并 —— **Map 的条目不是自有可枚举属性**，
`Object.assign` 只会复制出一个空对象。

**解决**：`readCatalogAt()` 改为遍历 `Map` 转成普通对象后返回。

**结论（通用规则）**：凡「返回集合」的内部函数，先看清调用方是用 `Object.assign`/展开合并
（⇒ 必须普通对象），还是用 `Map` API 访问。本次由新增的等价性单测当场抓到。

## 六、写路径与迁移纪律

### 6.1 写路径

```
saveCatalogMap(map) / patchCatalog(id, entry)
  → 记录数组
  → index-store.writeIndexAtomic()   // JSONL：原子全量重写（临时文件 + rename）
```

### 6.2 迁移必须「同步、且在读取之前」

若异步：迁移期间新落的总表会先建出**只含新记录**的 `.jsonl`；迁移脚本见目标已存在即跳过
⇒ 下次加载以 `.jsonl` 为准 ⇒ **旧总表丢失**。同步执行没有这个窗口。

### 6.3 命令

```bash
node scripts/migrate-json-index-to-jsonl.cjs --dir json/index --profile iwara            # 预演（默认）
node scripts/migrate-json-index-to-jsonl.cjs --dir json/index --profile iwara --apply    # 执行
node scripts/migrate-json-index-to-jsonl.cjs --dir json/index --profile iwara --apply --verify full
```

四条特性：**默认预演**（不动盘）/ **幂等**（目标存在即跳过）/ **可回滚**（旧文件进 `.trash`）/
**自校验**（回读校验记录数；`--verify full` 做对象级等价，失败则保留旧文件）。

启动时同步调用，失败只告警、不阻塞启动。`--profile iwara` 只迁总表；sidecar 与 `json/profile/` 一律不动。

## 七、导出/导入必须同一格式

原则：**产出与消费必须同格式** —— 改了存储却把导出留在缩进 JSON 是不自洽的。

| 端点 / 位置 | 改造后 |
|---|---|
| `GET /api/index/export` | 附件名 `iwara-index-<日期>.jsonl`、`Content-Type: application/x-ndjson`，内容**就是磁盘索引本身**（一行 meta + 一行一条） |
| `POST /api/index/import` | 吃导出的 JSONL 原文（`{json:"<文本>"}` 或直接 POST 原文），同时兼容旧 JSON（`{videos:…}` / `{items:[…]}` / `{dump:…}` / 扁平 map） |
| `GET /api/search/export` | `iwara-search-records-<日期>.jsonl`（一行 meta + 一行一条记录） |
| `POST /api/search/import` | 同上：JSONL 与旧 JSON（数组 / `{results:[…]}`）都吃 |
| 前端（`server/public/app.js`） | 两个下载名改 `.jsonl`；导入改为**把文件原文直接发给服务端**（不在浏览器 `JSON.parse` —— JSONL 整体不是合法 JSON） |

证据：单测里有一条**往返断言** —— 导出 → `importPayload` 原样导入 → 再导出，**逐字节一致**。

`GET /api/index`（列表）与 `GET /api/index-sidecar`（单条 sidecar）**未改**。

## 八、为什么是 JSONL，而不是 SQLite

存储层内置两种后端，默认走 JSONL；SQLite 只作可选后端，本节给实测与结论。

### 8.1 实测（双臂同机、同一份数据）

| 指标 | 24.9 万条 / 12 base | 75 万条 / 12 base |
|---|---|---|
| ① 启动加载 `load()` | JSONL **673ms** ／ SQLite 1.09s ⇒ **0.62×** | JSONL **2.37s** ／ SQLite 4.71s ⇒ **0.50×** |
| ② 单游戏增量写（改 1 条） | JSONL 35.1ms ／ SQLite **28.7ms** ⇒ 1.22× | JSONL 242ms ／ SQLite **212ms** ⇒ 1.14× |
| ③ 全库增量写（各改 1 条） | JSONL **353ms** ／ SQLite 385ms ⇒ 0.92× | JSONL **2.47s** ／ SQLite 2.55s ⇒ 0.97× |
| ④ 落盘体积 | JSONL 48.5MB ／ SQLite 56.5MB + WAL 20.9MB | JSONL 146.7MB ／ SQLite 187.4MB + WAL 31.3MB |

```bash
node scripts/bench-index-store.cjs --synthetic 83000  --bases 12 --iters 5   # ≈24.9 万条
node scripts/bench-index-store.cjs --synthetic 250000 --bases 12 --iters 3   # ≈75 万条
node scripts/bench-index-store.cjs --dir json/index --iters 5                # 真实索引（只读）
```

读法：写入看 `min`/`p50`；`avg` 会被 WAL 自动 checkpoint 的尖峰带偏（实测 min 109ms / avg 666ms）。

### 8.2 根因

1. **成本在序列化，不在文件写**：调用方每次传全量记录，逐条 `JSON.stringify` 两份后端都要付；
   JSONL 写整份落页缓存近乎免费，SQLite 省下的 I/O 抵不过「行 → 对象」反序列化
2. **载入更贵**：从库读要物化行对象 + 逐行 `JSON.parse`；而载入是每次启动都付的固定成本
3. **体积更大**：行内存值 JSON 文本 + 主键索引；WAL 是额外开销

### 8.3 与「下载任务列表」的对比（同样换库，结论相反）

| | 下载任务列表 | 索引 / 总表 |
|---|---|---|
| 写入形态 | **小而频繁** | **大而整份** |
| 载入权重 | 可忽略 | 每次启动全量载入，权重最高 |
| 实测 | 增量落盘 134ms → **30ms（4.5×）** | 启动加载 **慢 1.6–2×**，写入打平 |
| 结论 | **划算** | **不划算，回退** |

⇒ 判据：**「写入频繁且单次小、载入不重要」才适合换库**。

### 8.4 现状

- 默认 **JSONL 优先**；SQLite 需显式开关（且 `node:sqlite` 可用）
- 回退点：`index-store.js` 的 `sqliteEnabled()` + `readIndex` / `writeIndexAtomic` / `listBases` 的读取顺序

## 十、运维与排查

- `json/index/` 在 `.gitignore` 中，索引**不入库**
- **残留 `index.db`**：工作区当前存在一个 **0 字节的 `index.db`**（早期实验残留）。
  默认读路径是文件优先 ⇒ 它**不会被读到**、无副作用；确认无用可移入 `.trash`
- 常见现象与判断：
  - **搜索/列表无结果** → ① 总表为空 ② `.jsonl` 坏行过多（看 `badLines`）③ 迁移失败（看启动日志告警）
  - **`hasVideo()` 恒 false 但文件看着有内容** → 先怀疑「返回 Map 与 `Object.assign` 合并」那类类型不匹配（见第五节）
  - **想回退迁移** → 从 `json/index/.trash/<时间戳>-<原名>` 移回
- 做格式变更前，建议整目录打包到 `json/.trash/pre-<变更>-<时间戳>.tar.gz`（历史做法：131KB）

## 十一、已知边界

- 追加会产生同键重复行；载入时若重复行超过实时键数 1.5 倍会**自动压缩**一次
- **sidecar**（`<id>.json`）与 `json/profile/` 不在本体系内，格式保持缩进 JSON
- 本体系不含查询/搜索业务逻辑
- 存储层是独立模块，改动它需同时确认 `index-store.js` 与 `jsonl-store.js` 两侧契约一致
